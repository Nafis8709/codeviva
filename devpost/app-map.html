CodeViva — where things live

A snapshot of the finished proof of concept (source commit b30df28, Oct 26 2026). The code can drift after this; the paths and function names below are the anchors to search for.

The app in four pieces

  • The page (public/index.html, public/styles.css, public/app.js) — setup, viva and report screens. Holds the whole session in one state object.
  • The server (server.js) — serves the page and four JSON routes. Stateless: every request carries the files and history.
  • The examiners (src/examiners/) — the AI examiner (prompt → model → validation) and the labelled demo examiner (scripted, no AI). Same three functions: askQuestion, grade, report.
  • The guards (src/code.js, src/scoring.js) — snap model line numbers onto real code, and compute the ownership score without the AI.

One action, end to end: “Submit answer”

Reads the answer box, sends the files, settings, history, current question and answer to the server, then either asks the follow-up, fetches the next question, or finishes the viva.

Stop 2 — server.js → /api/viva/grade, then src/examiners/aiExaminer.js → grade

The server enforces the one-follow-up rule. The examiner asks the model, then lets the score decide the verdict so the stamp, the heatmap and the total can never disagree.

Stop 3 — public/app.js → heatRegions and renderCode

Each examined region takes its final verdict (a follow-up’s better result wins) and the code viewer adds a heat-solid, heat-partial or heat-gap class to those lines. The report reuses the same viewer as the heatmap.

A practice to reuse

Never trust a model’s structured output — validate it against reality. The spec’s open question was whether a small free model would return correct line numbers (spec.md > Decisions and Open Issues). Instead of hoping, the design sends numbered code, demands a fixed JSON shape, and repairs every reply with clampRange. test/ai.test.js proves it with a fake model that returns a wrong file name and line 400 of a 30-line file.

On your next AI feature: write down what the model must return, then write the check that rejects or repairs anything else — before you build the screen that displays it.
